## Invoices

An invoice is created automatically for every subscription purchase and renewal, and is inserted already marked `paid` (the wallet is debited synchronously, so there's no separate awaiting-payment step). Invoices are read-only from the user's perspective. There is currently no dedicated admin invoice list — invoices are visible per-user via their linked subscription/wallet transactions on **Admin → Users → [user]**.

### Numbering

Invoice numbers are **not** sequential. On a purchase, the number is `<prefix><YYYYMMDD><8 random hex chars>` (e.g. `INV-2026070412ab34cd`), where the prefix comes from the `billing_invoice_prefix` setting configured in **Admin → Billing → Settings**. The renewal worker follows the same pattern. The one exception is manual subscription extension, which currently hardcodes the `INV-` prefix regardless of what's configured.

### Line items

Each invoice contains one or more line items with:

| Field | Description |
|---|---|
| Description | Human-readable label (e.g. "Minecraft Basic — 1 month") |
| Quantity | Number of units (typically 1) |
| Period start | Subscription start date |
| Period end | Subscription end date |
| Unit price | The plan's list price for the tier, before any coupon discount |
| Total | `quantity × unit price` — this is **not** discounted; it always equals the full price |

Discount and tax are tracked at the invoice level (`discountCents`, `taxCents`), not per line item — a purchased invoice's `totalCents` is the line item subtotal minus `discountCents`.

### Statuses

The invoice status column supports five values, but the current purchase and renewal code only ever inserts an invoice as `paid` — there's no code path that creates a `draft`/`open` invoice or later transitions one to `uncollectible`/`void`.

| Status | Meaning | Used today? |
|---|---|---|
| `paid` | Payment confirmed | Yes — every invoice is created in this state |
| `draft` | Created but not yet finalized | No |
| `open` | Awaiting payment | No |
| `uncollectible` | Marked as unrecoverable | No |
| `void` | Canceled before payment | No |

### VAT

The invoice record has fields for a tax rate, VAT number, and billing address (street, city, country, postal code), and there are `billing_tax_enabled`/`billing_vat_rate`/`billing_require_vat_number` settings in **Admin → Billing → Settings**. However, none of these are currently read by the purchase or renewal code — `taxCents` is always `0` and the VAT/address fields are never populated. Treat VAT as schema support for a feature that isn't wired up yet, not as working tax calculation.

## Coupons

Coupons let you offer discounts on subscription purchases, checked and redeemed during the purchase wizard's confirmation step.

<Callout type="warn">
  There is currently no admin UI or API endpoint to create, list, or edit a coupon. The redemption logic below works if a coupon row exists, but the only way to create one today is a direct database insert into `billing_coupons`.
</Callout>

### Coupon fields

| Field | Description |
|---|---|
| Code | Uppercase alphanumeric code users enter at checkout |
| Type | `percentage` (e.g. 20% off) or `fixed` (e.g. $5 off) |
| Value | The discount amount |
| Max redemptions | Maximum total uses across all users. Leave unset for unlimited. |
| Redeem by | Optional expiry date after which the code is rejected |
| Applies to | Restrict to one plan, or leave unset to apply to any plan |

### Using a coupon

During the purchase wizard's confirmation step, users enter a coupon code. The panel:

1. Validates the code (active, not expired, not over the redemption limit, applies to the selected plan, not already used by this user)
2. Calculates the discount and subtracts it from the invoice total (the line item itself still shows the full price)
3. Records a coupon redemption and increments the coupon's `timesRedeemed` count

Each user can redeem a given coupon at most once — this is a hard limit (enforced by a unique constraint on coupon + user), not a configurable per-user cap.
